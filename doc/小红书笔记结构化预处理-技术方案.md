| 项目 | 内容 |

| 输入 | 已有结构化数据（JSON / CSV / DB） |

---

## 1. 前提与设计边界

### 1.1 规模决定架构

**500 篇以内是一个关键分水岭**，它让很多"标准做法"变成过度工程：

| 常见做法 | 本方案是否采用 | 理由 |
|---|---|---|
| 向量数据库 | ❌ 不用 | 500 篇用标签过滤足够，加向量库徒增复杂度 |
| 分布式任务队列 | ❌ 不用 | 单机 asyncio 并发即可 |
| 复杂增量调度 | ❌ 不用 | 全量重跑仅需数分钟，直接重跑更简单 |
| 独立服务部署 | ❌ 不用 | 一个离线脚本 + SQLite |
| 结构化输出约束 | ✅ 用 | 保证下游可解析 |
| 内容哈希幂等 | ✅ 用 | 避免重复付费 |

> **核心判断**：全量重跑成本 ≈ 400 次 Flash 调用 ≈ 数分钟 + 数元。
> 既然重跑这么便宜，**就不要为"增量"设计复杂机制**——出问题直接重跑。

### 1.2 数据流

```
已有结构化数据 (JSON/CSV/DB)
        ↓  ① 归一化 Normalize
   统一 RawNote 结构
        ↓  ② 清洗 Clean（规则，不花钱）
   去噪后的文本
        ↓  ③ 提炼 Extract（LLM，Flash）
   StructuredNote
        ↓  ④ 校验 Validate
   写入 SQLite
        ↓
   下游：标签过滤 → 攻略生成
```

## 2. 核心设计难点：多品类混杂

### 2.1 三种方案对比

多品类是本方案最关键的设计点。三条路：

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 大一统 Schema | 所有字段并集，一个 prompt | 字段大量为 null，模型困惑，token 浪费 |
| B. 先分类再分别提炼 | 两次调用 | 调用翻倍，延迟翻倍 |
| **C. 分层 Schema，单次调用** | 公共字段 + 品类扩展块 | ✅ **推荐** |

### 2.2 采用方案 C：分层 Schema

**设计思路**：让模型在**一次调用**中同时完成「判断品类」和「按该品类提炼」。

```
StructuredNote
├── 公共层 (所有品类必填)
│   ├── id / category / title
│   ├── location: {city, area}
│   ├── summary          ← 一句话概括
│   ├── key_points[]     ← 3-5 条要点，信息密度最高的部分
│   ├── tags[]
│   └── raw_ref          ← 原文引用，永不丢失
│
└── 扩展层 (按 category 二选一，其余为空)
    ├── place   : {name, address, price_level, hours, booking}
    ├── food    : {name, dishes[], price_per_person, queue}
    ├── product : {brand, item, price, pros[], cons[]}
    ├── stay    : {name, room_type, price_per_night, nearby}
    └── generic : {}   ← 兜底，不强行归类
```

### 2.3 品类枚举

保持**扁平且少**——品类越多，分类越不稳定。

| category | 覆盖内容 | 扩展块 |
|---|---|---|
| `place` | 景点、展馆、公园、拍照点 | place |
| `food` | 餐厅、咖啡、小吃、探店 | food |
| `shopping` | 好物、护肤、穿搭、数码 | product |
| `stay` | 酒店、民宿 | stay |
| `guide` | 行程规划、经验帖、避坑 | generic |
| `other` | 无法归类 | generic |

> **关键原则：允许模型输出 `other`。**
> 强迫分类会产生错误标签，而错误标签比无标签危害更大——下游过滤时会漏召回。

## 3. 处理流程详述

### 3.1 阶段一：归一化

你已有结构化数据，但字段名可能不统一。先统一到 `RawNote`：

```python
from dataclasses import dataclass
from typing import Optional
import hashlib

@dataclass
class RawNote:
    id: str
    title: str
    content: str
    author: Optional[str] = None
    collected_at: Optional[str] = None
    url: Optional[str] = None
    images: list[str] = None

    @property
    def content_hash(self) -> str:
        """用于幂等：内容不变则跳过重新提炼"""
        s = f"{self.title}|{self.content}"
        return hashlib.md5(s.encode()).hexdigest()[:16]
```

**字段映射配置化**，不同来源用不同映射表：

```python
FIELD_MAP = {
    "note_id": "id", "desc": "content", "display_title": "title",
    "note_url": "url", "time": "collected_at",
}
```

### 3.2 阶段二：规则清洗（不花钱的那步）

**先用规则砍掉一半噪音，再送给模型。** 这一步零成本，但能显著降低 LLM 输入 token。

```python
import re

EMOJI_RE = re.compile(
    "[\U0001F300-\U0001FAFF\U00002600-\U000027BF\u2190-\u21FF\uFE0F]"
)
NOISE_PATTERNS = [
    r"#\S+",                      # 话题标签（另行提取）
    r"@\S+",                      # @用户
    r"(求关注|点赞收藏|姐妹们冲|码住|不踩雷|谁懂啊|绝了)+",
    r"[!！]{2,}", r"[?？]{2,}", r"[~～]{2,}",
    r"\.{3,}",
]

def clean(text: str) -> str:
    tags = re.findall(r"#(\S+)", text)          # 话题先存下来，是有用信息
    text = EMOJI_RE.sub("", text)
    for p in NOISE_PATTERNS:
        text = re.sub(p, " ", text)
    text = re.sub(r"\s{2,}", " ", text).strip()
    return text, tags
```

**实测经验**：小红书原文经规则清洗后，字符数通常下降 25–40%，且不损失实质信息。

### 3.3 阶段三：LLM 提炼

#### Prompt 设计

```python
SYSTEM_PROMPT = """你是笔记信息提取器。将小红书笔记提炼为结构化 JSON。

规则：
1. 只提取笔记中明确写到的信息，不推测、不补充常识
2. 无法确定的字段留空字符串或空数组，不要编造
3. category 从枚举中选择；无法明确归类时选 other，不要强行归类
4. key_points 提取 3-5 条最具决策价值的信息（价格、排队、预约、
   营业时间、避坑提醒等），每条不超过 20 字
5. summary 一句话，不超过 30 字
6. 只输出 JSON，不要 markdown 代码块，不要任何解释"""

USER_TMPL = """标题：{title}
正文：{content}
话题标签：{tags}"""
```

#### 结构化输出约束

**必须用 API 的结构化输出能力**，不要靠 prompt 里写"请输出 JSON"然后正则解析——那是不稳定的。

```python
RESPONSE_SCHEMA = {
    "type": "object",
    "required": ["category", "summary", "key_points"],
    "properties": {
        "category": {
            "type": "string",
            "enum": ["place","food","shopping","stay","guide","other"]
        },
        "city":     {"type": "string"},
        "area":     {"type": "string"},
        "summary":  {"type": "string"},
        "key_points": {"type": "array", "items": {"type": "string"}},
        "tags":     {"type": "array", "items": {"type": "string"}},
        "ext": {
            "type": "object",
            "properties": {
                "name":  {"type": "string"},
                "price": {"type": "string"},
                "dishes":{"type": "array", "items": {"type": "string"}},
                "hours": {"type": "string"},
                "booking": {"type": "string"},
                "pros":  {"type": "array", "items": {"type": "string"}},
                "cons":  {"type": "array", "items": {"type": "string"}},
            },
        },
    },
}

resp = client.generate_content(
    contents=[...],
    generation_config={
        "response_mime_type": "application/json",
        "response_schema": RESPONSE_SCHEMA,
        "temperature": 0.1,          # 抽取任务，要稳定不要创意
    },
)
```

> `ext` 用宽松 object 而非严格 oneOf——严格约束在多品类下容易触发模型报错，
> 宽松定义 + 后置校验更稳。

#### 模型选型

| 环节 | 模型 | 理由 |
|---|---|---|
| 笔记提炼 | **Flash 级** | 抽取任务不需要强推理，快且便宜 |
| 疑难重试 | Pro 级 | 仅对 Flash 失败的少数样本降级使用 |

### 3.4 阶段四：并发执行

500 篇串行会很慢，用 asyncio 控制并发：

```python
import asyncio, json

async def extract_one(note: RawNote, sem: asyncio.Semaphore) -> dict:
    async with sem:
        for attempt in range(3):
            try:
                text, tags = clean(note.content)
                resp = await call_llm(note.title, text, tags)
                data = json.loads(resp.text)
                return {**data, "id": note.id,
                        "raw_ref": note.url,
                        "content_hash": note.content_hash,
                        "status": "ok"}
            except Exception as e:
                if attempt == 2:
                    return {"id": note.id, "status": "failed",
                            "error": str(e),
                            "fallback_text": note.content[:300]}
                await asyncio.sleep(2 ** attempt)   # 指数退避

async def run(notes: list[RawNote], concurrency: int = 8):
    sem = asyncio.Semaphore(concurrency)
    return await asyncio.gather(*[extract_one(n, sem) for n in notes])
```

**并发数建议从 5–8 起步**，观察是否触发 429 再调整。API 速率限制以官方文档为准。

**耗时估算**（400 篇，并发 8，单次约 3s）：`400 / 8 × 3s ≈ 150s`

### 3.5 阶段五：校验与落库

```python
def validate(item: dict) -> tuple[bool, list[str]]:
    issues = []
    if item.get("status") != "ok":
        return False, ["extraction_failed"]
    if not item.get("summary"):
        issues.append("empty_summary")
    if len(item.get("key_points", [])) < 2:
        issues.append("too_few_key_points")
    if item.get("category") == "other":
        issues.append("uncategorized")     # 不算错误，但需人工抽查
    return len(issues) == 0, issues
```

#### 存储：SQLite 足够

```sql
CREATE TABLE notes (
    id            TEXT PRIMARY KEY,
    category      TEXT NOT NULL,
    city          TEXT,
    area          TEXT,
    summary       TEXT,
    key_points    TEXT,          -- JSON array
    tags          TEXT,          -- JSON array
    ext           TEXT,          -- JSON object
    raw_ref       TEXT,
    content_hash  TEXT,          -- 幂等依据
    status        TEXT,
    issues        TEXT,
    updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_city_cat ON notes(city, category);   -- 下游过滤主路径
CREATE INDEX idx_hash     ON notes(content_hash);
```

#### 幂等逻辑

```python
def need_process(note: RawNote, db) -> bool:
    row = db.execute(
        "SELECT content_hash, status FROM notes WHERE id=?", (note.id,)
    ).fetchone()
    if not row:            return True     # 新笔记
    if row[1] != "ok":     return True     # 上次失败，重试
    return row[0] != note.content_hash     # 内容变了才重跑
```

## 4. 效果预估

以 400 篇、单篇 500 字为例：

| 指标 | 优化前 | 规则清洗后 | LLM 提炼后 |
|---|---|---|---|
| 单篇字符 | ~500 | ~330 | ~80 |
| 单篇 token | ~600 | ~400 | **~120** |
| 全库 token | 24 万 | 16 万 | **4.8 万** |
| 压缩率 | — | 33% | **80%** |

**结合下游标签过滤**（只送 20 篇）：

```
优化前：400 篇 × 600 token = 240,000 token / 请求
优化后： 20 篇 × 120 token =   2,400 token / 请求
                              ↓
                        降低 99%
```

> 注意：真正的收益来自 **预处理 × 检索过滤** 的乘法效应，
> 单做预处理只降 80%，两者叠加才是数量级变化。

## 5. 质量保障

### 5.1 抽样验收

预处理是**离线一次性任务，错了会污染整个下游**，必须验收：

- 随机抽 30 篇人工比对
- 每个 category 至少覆盖 3 篇
- 重点检查 `other` 类占比

| 检查项 | 通过标准 |
|---|---|
| category 准确率 | ≥ 90% |
| key_points 无编造 | 100%（零容忍） |
| 关键信息未丢失（价格/地址/预约） | ≥ 95% |
| `other` 占比 | ≤ 15%（过高说明品类设计有问题） |

### 5.2 编造是最大风险

抽取任务里，**模型幻觉出一个不存在的价格或地址**，比字段留空危害大得多——下游会把它当事实写进攻略。

防御手段：
1. Prompt 明确「不推测、不补充常识」
2. `temperature=0.1`
3. 抽检时**专门查证 key_points 里的数字**（价格、时长、距离）
4. 永久保留 `raw_ref`，可回溯原文

### 5.3 失败降级

```
提炼失败 → 保留原文前 300 字作为 fallback_text
         → status='failed'，下游仍可使用，只是不参与标签过滤
         → 不阻塞主流程
```

## 6. 实施步骤

| 步骤 | 内容 | 工作量 |
|---|---|---|
| 1 | 数据探查：统计品类分布、字段完整度、平均长度 | 2h |
| 2 | 写归一化 + 规则清洗，**先跑 20 篇看效果** | 3h |
| 3 | 设计 Schema + Prompt，20 篇小样本调优 | 4h |
| 4 | 补并发 + 重试 + 幂等，全量跑一遍 | 3h |
| 5 | 抽样验收 30 篇，修正 Prompt 后重跑 | 3h |
| 6 | 落库 + 建索引，联调下游过滤 | 2h |

**合计约 2 天。**

> **强烈建议第 2、3 步都先用 20 篇小样本。**
> 全量跑一次虽然只要几分钟，但 Prompt 没调好就全量跑，
> 会反复浪费时间在等待上。小样本迭代快得多。

## 7. 风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| **模型编造信息** | 攻略出现虚假价格/地址 | temperature 低 + prompt 约束 + 抽检数字 |
| 品类分类错误 | 下游过滤漏召回 | 允许 other；抽检 category 准确率 |
| 提炼丢失关键细节 | 用户收藏的重点没进攻略 | 保留 raw_ref；key_points 优先保留决策信息 |
| 并发触发限流 | 任务中断 | 并发数可配置；指数退避重试 |
| Schema 变更需重跑 | 时间成本 | 500 篇重跑仅数分钟，可接受 |
| 原始数据字段不一致 | 归一化出错 | 映射表配置化；步骤 1 先做数据探查 |

## 附录：设计决策速查

1. **500 篇以内不上向量库** —— 标签过滤够用，SQLite 索引足够快。
2. **分层 Schema 而非大一统** —— 公共字段 + 品类扩展块，一次调用完成。
3. **允许 `other`** —— 错误标签比无标签更有害。
4. **规则清洗在 LLM 之前** —— 零成本降 33% token。
5. **必须用结构化输出 API** —— 不要正则解析模型输出。
6. **用 Flash 不用 Pro** —— 抽取任务不需要强推理。
7. **重跑比增量简单** —— 这个规模下别设计复杂调度。
8. **永远保留 raw_ref** —— 提炼有损，原文是唯一退路。
9. **小样本先行** —— Prompt 调优阶段永远只用 20 篇。
10. **编造零容忍** —— 抽检时专门查证数字。
